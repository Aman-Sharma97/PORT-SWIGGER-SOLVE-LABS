
# SameSite Strict bypass via client-side redirect

This lab's change email function is vulnerable to CSRF. To solve the lab, perform a CSRF attack that changes the victim's email address. You should use the provided exploit server to host your attack.

You can log in to your own account using the following credentials: wiener:peter

Hint: You cannot register an email address that is already taken by another user. If you change your own email address while testing your exploit, make sure you use a different email address for the final exploit you deliver to the victim.

The redirect is generated by JavaScript in `/resources/js/commentConfirmationRedirect.js`:

```
redirectOnConfirmation = (blogPath) => {
    setTimeout(() => {
        const url = new URL(window.location);
        const postId = url.searchParams.get("postId");
        window.location = blogPath + '/' + postId;
    }, 3000);
}
```



**Pic 6**


The behavior is controlled by requests to `/post/comment/confirmation?postId=a`. Changing `postId` can make the redirect target a path such as:

```
/post/../my-account/change-email?email=test5%40test.com&submit=1
```

A request to test this behavior looks like:

```
/post/comment/confirmation?postId=../my-account/change-email?email=test7%40test.com&submit=1
```

The redirect reaches the intended endpoint, but the `submit` parameter is missing:



**Pic 7**


To keep the parameter within the `postId` value, replace `&` with its URL-encoded form, `%26`:

```
/post/comment/confirmation?postId=../my-account/change-email?email=test7%40test.com%26submit=1
```

With that encoding, the request works:
